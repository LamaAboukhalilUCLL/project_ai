## 1. Introduction

Slow SQL queries degrade application performance invisibly, they don't crash, they just take longer than necessary and waste time. We built a live PostgreSQL monitor that automatically detects slow queries, rewrites them using a fine-tuned large language model, and verifies that the rewrite is genuinely faster before storing it.

The system monitors a Stats Stack Exchange database available publicly at https://ia800508.us.archive.org/view_archive.php?archive=/30/items/stackexchange/stats.stackexchange.com.7z  (~345k users, 425k posts, 1.7M votes) and routes any query exceeding 100ms through a four-component AI pipeline: a neural classifier, an LLM generator, a neural ranker, and a database verifier.

---

## 2. Data

**Classifier training data:** 1,438 SQL queries measured against the real PostgreSQL database. Each query was run with a cold cache flush (`DISCARD ALL`) followed by warm runs (median of 2–5 repetitions). Features: 8 lexical patterns (regex-derived) + 12 EXPLAIN ANALYZE plan features. Label: `slow` if warm median > 100ms, `fast` otherwise (~60% slow, ~40% fast).

**LLM fine-tuning data:** 250 (slow → optimized) SQL pairs generated by GPT-4o-mini with the database schema as context, covering 12 anti-patterns: `SELECT *`, correlated subqueries, multi-table JOINs, `LIKE` wildcards, `ORDER BY` without `LIMIT`, `UNION`, `CASE WHEN`, `EXISTS`, CTEs, window functions, self-joins, and date aggregations.

**Challenges:** Execution times are hardware-dependent and non-deterministic. Queries hitting the 10s timeout are recorded as 10,000ms, creating an artificial ceiling in the regression target. Generating diverse slow queries required parameterized templates with random sampling to avoid duplicates.

---

## 3. Model & Methods

**Multi-task neural classifier** (PyTorch): shared trunk (20→64→32, ReLU, Dropout 0.3) with two heads — classification (p_slow, BCE loss) and regression (predicted_ms, quantile loss τ=0.7). Joint loss: `α·BCE + (1−α)·Quantile` with α=0.6. Quantile loss was chosen over MSE to reduce under-prediction of slow queries, which is the more costly error for a monitor. Trained for 150 epochs on 1,154 queries (80/20 split).

**Fine-tuned LLM** (defog/sqlcoder-7b + QLoRA): `defog/sqlcoder-7b` was pre-trained on 20,000+ SQL queries by Defog.ai. We applied second-stage domain adaptation using QLoRA (4-bit NF4, LoRA rank=16), training only 13.6M of 7.25B parameters (0.19%) on our 250 pairs for 3 epochs (~10 minutes on RTX 5070 Laptop GPU). This teaches the model our specific schema and optimization patterns while preserving its existing SQL knowledge.

**Neural ranker:** the same classifier re-scores each of the 3 LLM candidates using their EXPLAIN ANALYZE features and sorts by predicted speedup against the actual pg_stat_statements baseline time.

**Embedding memory** (sentence-transformers/all-MiniLM-L6-v2): verified fixes are stored as embeddings. Before generating new candidates, the monitor retrieves semantically similar past fixes (cosine similarity ≥ 0.8) to guide the LLM toward known-good patterns.

## 4. Results & Evaluation

**Classifier (held-out test, n=284):**

| Metric | Value |
|---|---|
| Classification accuracy | 97.6% |
| Slow-class recall | 1.000 |
| Regression log-MAE | 0.716 (~2× avg error) |
| Regression R² (log scale) | 0.645 |

Slow-class recall of 1.000 means zero missed slow queries on the test set. R²=0.645 is sufficient for ranking — relative ordering of candidates matters, not absolute prediction.

**Pipeline comparison (16 queries, real DB execution):**

| Approach | Win rate | Avg speedup |
|---|---|---|
| GPT-only | 62.5% | −11.9% |
| Full pipeline | **75.0%** | **+18.1%** |

The full pipeline outperforms GPT-only by +12.5pp on win rate and +30pp on average speedup. GPT-only averages negative speedup — it makes queries slower on GROUP BY aggregations where the planner is already optimal.

**Live monitor run (8 queries, verified against DB):**

| Query pattern | Original | Fixed | Saved |
|---|---|---|---|
| `SELECT *` + `ORDER BY` | 405ms | 0.4ms | 404ms |
| 3-table JOIN `SELECT *` | 4318ms | 544ms | 3774ms |
| Correlated subquery AVG | 968ms | 567ms | 400ms |
| DISTINCT 3-table JOIN | 673ms | 291ms | 382ms |
| `LIKE` wildcard | 147ms | — | skipped (p=9.7%) |

7/7 verified wins. The classifier correctly skipped the LIKE query — plan features showed an index scan despite the wildcard, demonstrating the value of combining text and plan features.

## 6. Challenges & Future Work

**Challenges:**
- RTX 5070 Laptop that the main setup was done on uses Blackwell architecture (sm_120) — not supported by stable PyTorch, requiring nightly CUDA builds and Python 3.12 specifically.
- Execution time non-determinism: the same query can vary ±30% between runs due to caching, making labels noisy near the 100ms boundary (which is why we run SELECT pg_stat_statements_reset();  in PgAdmin before each test-run)
- The regression head is capped at 10,000ms due to `statement_timeout`, distorting the upper tail of the training distribution.
- We tried a lot of previous models, t5-small (this model knows nothing about coding, turned out to perform very badly given all the time and retraining done on it, due to the data limitation and the fact that it is text-based), codet5(small or base, did systematical errors, did not learn our database, and it was not trained well on sql). Which pushed us to use our current model, but fine-tune it again and adapt it to our own usage (still a much better alternative than our first gpt approach which was simple)
- The idea of the project turned out a bit complex to actually develop, a lot of setup, a lot of new unlearned strategies which required us to learn them first and try to understand what we are doing at every point, we were hopefull to train an LLM from scratch, but that would've required a lot of time and resources given the time limitations


**Future work: (may or may not be done)**
- Replace the hard 100ms threshold with a soft probability gate or learned threshold
- Add rule-based candidates (automatic index suggestions, column expansion) alongside the LLM to increase diversity
- Train the regression head on relative speedup (candidate/original) rather than absolute time for better hardware generalization
- Extend to multi-tenant monitoring with per-schema fine-tuning adapters
- Enhance the Dashboard
- Try generalizing it on many other databases
