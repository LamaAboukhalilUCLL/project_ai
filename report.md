## 1. Problem

Modern web applications run thousands of SQL queries per minute. Slow queries
degrade user experience invisibly — they don't crash, they just take longer than
they should. We built **a live monitor that detects slow PostgreSQL queries,
predicts how slow they are, generates and ranks candidate optimizations, and
verifies the top candidate against the database** before presenting a structured
response.

The system monitors a Stack Exchange dump (~71k users, 27k posts, 93k votes)
and routes any query whose mean execution time exceeds 100ms through the AI
pipeline below.

## 2. System architecture

*(insert architecture diagram here — see section C of the assistant message)*

The pipeline has six stages:

1. **Detection** — `pg_stat_statements` is polled every 5 seconds. Queries with
   `mean_exec_time > 100ms` are extracted and deduplicated against past picks.
2. **Feature extraction** — for each candidate query, we compute 20 features
   in two families: 8 lexical patterns derived via regex (e.g. `has_select_star`,
   `join_count`, `has_function_in_where`) and 12 features extracted by walking
   the JSON-formatted output of `EXPLAIN (ANALYZE, BUFFERS)` (planner cost,
   estimated/actual rows, buffer hits/reads, scan and join types).
3. **Discrimination** — a multi-task neural network with a shared 64→32 trunk
   and two heads (classification and regression) decides whether the query
   warrants optimization (`p_slow > 0.5`) and predicts its log execution time.
4. **Generation** — when a query passes the gate, a fine-tuned `{{ MODEL_NAME }}`
   model produces up to 3 candidate rewrites via beam search and temperature
   sampling. A regex-based validator filters malformed outputs before scoring.
5. **Ranking** — each candidate's predicted execution time is computed by the
   *same* multi-task model; candidates are sorted by predicted speedup vs the
   original. **This step is what makes the system more than text-in/text-out:
   the trained discriminator evaluates the generator's output, rather than the
   generator's first guess being treated as the answer.**
6. **Verification** — the top-ranked candidate is run against the live database
   with cold + warm timing to produce a measured speedup. Genuine wins are
   stored in a sentence-transformer embedding index for retrieval on future
   similar queries.

## 3. AI components

### 3.1 Multi-task neural network (the discriminator)

Inputs: 20 features. Architecture: shared trunk (Linear 64 → ReLU → Dropout
0.3 → Linear 32 → ReLU → Dropout 0.3) with two heads (each Linear 16 → ReLU
→ Linear 1). Total parameters: ~3.5k.

**Training objective**:

$$\mathcal{L} = \alpha \cdot \mathcal{L}_{\text{BCE}} + (1 - \alpha) \cdot \mathcal{L}_{\text{quantile}}(\tau=0.7)$$

with α=0.6. Quantile loss with τ=0.7 was chosen after the initial MSE-trained
model showed systematic under-prediction at the high end of the time
distribution. Under-prediction is the worse failure mode for a slow-query
monitor, so we biased the model upward.

**Test set (n=127)**: classification 92.9% accuracy, slow-class recall 0.97;
regression log-MAE 0.85, R² 0.69. **Stratified 20-query manual evaluation**:
classification 100% correct, log-MAE 0.76 (predictions off by an average factor
of 2.14×).

### 3.2 Fine-tuned query generator

We fine-tuned `{{ MODEL_NAME }}` (`{{ PARAM_COUNT }}` parameters) on
`{{ NUM_PAIRS }}` (slow query → optimized query) pairs. The optimized side was
generated by GPT-4o-mini with a schema-aware prompt. Best validation loss
{{ BEST_VAL_LOSS }} reached at epoch {{ BEST_EPOCH }}; the early-stopped
checkpoint is saved. Inference uses beam search (n_beams=4) plus two
temperature samples to produce a candidate set with diversity.

### 3.3 Model-in-the-loop ranking

For each candidate, the same multi-task model that predicted on the original
query also scores the candidate by re-extracting features and querying the
regression head. Candidates are sorted by predicted speedup (baseline_ms −
candidate_ms). The top candidate is verified against the live database; the
others are recorded but not run.

### 4.3 Defense of design decisions

- **Why a custom multi-task model and not a single regression head?** Two heads
  share representation while serving different downstream uses: the
  classification head gates the optimization pipeline, the regression head ranks
  candidates.
- **Why plan features when text features were already there?** *(write 2 sentences referencing the United States LIKE example: text features said "slow," planner-derived features said "fast," and the model correctly trusted the planner.)*
- **Why fine-tune a generator instead of relying on GPT?** The fine-tuned model
  serves as one of several candidate sources, and contributes the offline /
  cost-controlled portion of the candidate pool. Quality is not its principal
  contribution — the discriminator's ranking is.

## 5. Lecturer's feedback addressed

The four points raised during our consultation were:

| Concern | How addressed |
|---|---|
| **Project too simple, lacks advanced AI** | Replaced single-task MLP on 8 regex features with a multi-task neural network on 20 features (text + planner-derived). Added a fine-tuned seq2seq generator and a learned ranker. The pipeline integrates four ML components: discriminator, generator, ranker, embedding-based memory. |
| **Training dataset too small** | Grew from 465 to 633 queries (+36%) using parameterized template-based query generation that targets class imbalance and the decision boundary. |
| **Execution times unreliable** | Replaced single hot-cache run with cold (post-`DISCARD ALL`) + warm (median of multiple runs) measurements; adaptive run count for slow queries; explicit handling of 10s timeouts (capped, not dropped). |
| **Avoid pure text-in/text-out** | Pipeline does not return the generator's first guess. The trained discriminator scores each candidate's predicted speedup, ranks them, and the top one is verified against the live database before being returned. The AI component doing the actual decision-making is the discriminator + verifier loop, not the generator. |

## 6. Limitations and future work

- The 100ms slow/fast threshold is a hard cutoff; queries near 100ms are
  inherently ambiguous and inflate misclassification counts at the boundary.
- The 10-second `statement_timeout` creates an artificial ceiling: 18 queries
  in the training set hit the cap and are recorded as exactly 10000ms. They
  contribute correct slow/fast labels but distort the regression target by
  collapsing to a single value. A follow-up iteration should exclude these
  from the regression target (keeping them as a "cap-exceeded" signal for the
  classification head only).
- The fine-tuned generator was trained on outputs from GPT-4o-mini, so it
  cannot exceed the quality of its teacher. Ensemble with rule-based and direct
  GPT candidate sources would mitigate this.
- All measurements come from a single Stack Exchange dump on one machine.
  Calibration on different databases or hardware would require retraining.

The full pipeline is reproducible from a fresh clone:

python loading_data/local_data.py        # load XML data
python queries_generation/all_queries.py # measure 465 queries
python queries_generation/generate_queries.py  # template-generate 168 more
python classifier/classifier.py          # train discriminator
python finetune/build_dataset.py         # distill GPT into fine-tuning pairs
python finetune/finetune.py              # fine-tune generator
python monitor/monitor.py                # run live monitor
